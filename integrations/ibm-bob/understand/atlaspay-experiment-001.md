# AtlasPay UNDERSTAND Experiment 001 — IBM Bob PP4Z Native-First Procedure

**Framework:** v0.3.1  
**Estate:** AtlasPay  
**Capability:** Dynamic Transaction Limit  
**Goal:** Evaluate PP4Z-backed UNDERSTAND output against controlled AtlasPay ground truth without leaking the answer key into the model workspace.

## Principle

This experiment is not a test of whether generic prompts can recreate PP4Z. It tests whether verified PP4Z capabilities, composed through Agentic Strangler evidence contracts, produce decision-grade understanding.

## 0. Prepare an isolated workspace

Do not open the repository root as the scored Bob workspace because it contains `evals/atlaspay/ground-truth.yaml`.

Create a separate workspace containing only the AtlasPay estate and framework governance overlay. You can use `prepare-atlaspay-run.sh` in this directory.

The evaluator ground truth must remain outside Bob's accessible workspace.

## 1. Record run metadata

Record:

- run ID;
- date/time;
- IBM Bob version;
- PP4Z version/context;
- whether Z Understand is configured;
- model/provider settings if visible;
- source commit/tag;
- confirmation that ground truth is absent.

## 2. Establish native PP4Z context

In the isolated AtlasPay workspace:

1. configure/sign in to Z Understand where available;
2. generate the data dictionary using the native PP4Z workflow/command appropriate to the installed release;
3. confirm `DD.json` exists if generated by the installed workflow;
4. run `/init` so Bob generates repository-level `AGENTS.md`;
5. review the generated instructions before adding framework policy.

Do not replace these native setup steps with our generic prompts.

## 3. Merge the Agentic Strangler governance overlay

Open `AGENTS.framework.md` in the isolated workspace and merge its governance/evidence rules into the Bob-generated `AGENTS.md`.

Preserve useful product-generated application instructions. The overlay should add, not erase, native context.

Capture a diff or note describing what was added.

## 4. Run native UNDERSTAND capabilities first

### 4.1 Capability/application context

Use Z Architect mode and native explanation/documentation capabilities to establish AtlasPay application context.

### 4.2 Dependency and impact analysis

Use native `impact-analysis` / `/impact-analysis` with the Dynamic Transaction Limit change statement.

Save the unedited native output.

### 4.3 Business-rule context

Use the appropriate native program/application documentation workflow and data-dictionary context to recover business rules and exceptions.

Save the unedited native output.

## 5. Apply framework playbooks as evidence contracts

Compare native outputs against:

- `playbooks/discovery/playbook.yaml`
- `playbooks/dependency-analysis/playbook.yaml`
- `playbooks/rule-extraction/playbook.yaml`

At this point, do **not** use evaluator ground truth.

Identify only evidence-contract gaps such as:

- missing source references;
- no confidence classification;
- missing batch/data/middleware categories;
- unclear exception precedence;
- unreported unknowns.

## 6. Use supplemental prompts only for gaps

If required, use the repository prompts for missing evidence or normalization:

- capability discovery;
- change impact;
- business-rule extraction;
- known unknowns;
- SME questions.

Record which supplemental prompt was used and why.

## 7. Build the Current-State Evidence Pack

Synthesize native and supplemental outputs into the framework evidence template.

Each material claim should be categorized as:

- proven;
- strongly-supported;
- unresolved.

Also record:

- native capabilities used;
- supplemental assets used;
- evidence gaps;
- human questions;
- stage-exit recommendation.

## 8. Freeze the run

Before scoring:

- save all raw outputs;
- save final evidence pack;
- save screenshots;
- record hashes/commit if practical;
- make no manual corrections to the frozen answer.

## 9. Evaluate outside the Bob workspace

Only now compare the frozen outputs against:

`evals/atlaspay/ground-truth.yaml`

Use the UNDERSTAND evaluation suite for:

- Dependency Recall;
- Business Rule Recall;
- Evidence Traceability;
- Unsupported Claim Rate;
- Known-Unknown Detection;
- Impact Analysis Completeness.

## 10. Diagnose misses

Classify each material miss as:

- **native-context/configuration issue**;
- **framework evidence-contract issue**;
- **supplemental prompt issue**;
- **source-estate ambiguity**;
- **human/domain-knowledge requirement**.

Do not automatically solve every miss by adding more prompts.

## Screenshot targets

Capture at least:

1. PP4Z/Z Architect analysis of the AtlasPay capability;
2. native impact analysis exposing a non-obvious dependency;
3. business-rule/documentation output with source context;
4. an uncertainty or human-validation point, if available.

All screenshots must use synthetic AtlasPay content only.
